삐뽀삐뽀 / TEAM CONCEPT NOTE

“모든 안전수칙은
피로 쓰인다.”

사고가 일어난 뒤에야 부족했던 안전수칙을 발견해 왔습니다.
우리는 실제 피해가 발생하기 전에, 가상의 행사장에서 위험을 먼저 찾아보려 합니다.

팀원에게 공유하는 제품 방향 · 시뮬레이션 설계 설명

같은 행사장에서도 어떤 사람들이 있는지,
어떤 일이 발생하는지에 따라 결과는 달라집니다.
01 / 우리가 바꾸어 보는 두 가지

사람의 변화 × 환경의 변화

① 사람의 변화

가상 사람마다 다른 특성을 부여합니다. 이것이 페르소나입니다.

이동 속도공간에 대한 익숙함위험 인지·반응 시간동행자 유무이동 지원 필요 여부
  • 랜덤 생성: 여러 특성을 무작위로 조합해 예상하지 못한 참가자 구성을 탐색합니다.
  • 입력 정보 기반: 예상 인원, 연령 구성, 행사 유형 등의 정보를 바탕으로 참가자 구성을 만듭니다.
같은 조건에서도 랜덤 시드를 바꾸어 여러 번 실행합니다. 나이만으로 행동을 단정하지 않고, 행동 특성을 별도 변수로 둡니다.

② 환경의 변화

행사 중 일어날 수 있는 사건을 트리거로 발생시킵니다.

화재·연기 발생출입구 폐쇄정전특정 구역 혼잡안내 방송 지연
  • 임의의 사건: 미리 정한 범위 안에서 사건의 종류·위치·시점·강도를 바꾸어 발생시킵니다.
  • 조건 비교: 같은 사건에서 출구 개방이나 안내 인력 배치를 바꾸어 결과를 비교합니다.
환경 변화는 건물 모양을 바꾸는 것만이 아닙니다. 시간에 따라 달라지는 사건과 운영 상태도 포함합니다.
02 / 시뮬레이션이 답해야 할 질문

“무슨 사고가 날까?”에서
“무엇을 바꾸면 위험이 줄어들까?”까지

관찰할 결과

  • 어느 구역에 사람이 몰리고, 병목이 생기는가?
  • 모두 이동하는 데 얼마나 걸리는가?
  • 어떤 특성의 사람이 이동을 완료하지 못하는가?
  • 작은 사건이 혼잡·이동 지연으로 이어지는가?

비교할 개선안

  • 출구 하나를 더 열면 병목이 줄어드는가?
  • 안내 인력을 옮기면 이동 흐름이 나아지는가?
  • 정원을 줄이거나 통로를 확보하면 효과가 있는가?
  • 어떤 조치를 가장 먼저 해야 하는가?

핵심은 사람이 죽는 장면을 만드는 것이 아니라, 실제 행사 전에 개선할 근거를 찾는 것입니다.

사망·부상 수치를 제시하려면 검증된 위해 모델이 필요합니다. 초기 시연에서는 대피 시간, 병목, 미대피 인원 등 관찰 가능한 지표를 사용합니다.

03 / 한 번의 실행은 이렇게 연결됩니다

입력 → 반복 실험 → 기억 → 조치 제안

STEP 1행사 조건 입력

공간 구조·출입구·예상 인원·참가자 정보

STEP 2조합을 바꿔 실행

페르소나 구성과 환경 트리거를 바꾸며 반복

STEP 3Agent가 분석·기억

조건·관찰 결과·실패 사례·개선안의 효과 저장

STEP 4관리자에게 제안

긴급성·예상 효과·비용으로 조치 우선순위 제시

시뮬레이터가 사람의 이동과 지표를 계산하고, LLM Agent는 그 결과를 설명·비교·기억합니다. LLM의 설명 자체를 물리적 검증으로 취급하지 않습니다.

04 / 팀 이해를 위한 조합 예시

사람과 사건을 바꾸면 질문도 달라집니다.

아래는 설명용 시나리오 카드입니다. 실제 시뮬레이션이나 측정 결과를 생성하지 않습니다.

실제로 구현할 때는 이 조건을 시뮬레이터에 전달하고, 결과를 기록한 뒤 개선 전후를 비교합니다.

05 / 우리가 만드는 제품의 두 축

행사 전에는 대비하고,
행사 중에는 발견하고 대응합니다.

행사 전 · 위험 탐색

사람과 환경을 바꾼 반복 시뮬레이션으로 위험 조건을 찾고, 개선 조치를 비교합니다.

산출물: 위험 구역, 발생 조건, 비교 결과, 조치 우선순위

행사 중 · 실시간 감지

카메라 영상에서 화재·낙상 등의 위험 신호를 감지하고, 관리자 확인과 대응 흐름으로 연결합니다.

산출물: 감지 시각, 카메라 위치, 근거 화면, 확인·조치 기록

두 기능은 연결되지만 별도로 검증합니다. 시뮬레이션 결과가 실제 사고 예측 정확도를 보장하거나, 탐지 모델이 모든 사고를 발견하는 것은 아닙니다.

06 / 이번 데모의 구현 기준

한 공간, 몇 가지 조합, 개선 전후 비교

  • 공간: 행사장 한 곳의 통로와 출구를 단순화하여 구현합니다. 사진·영상 기반 3D 재구성은 공간 제작 수단이며, 이동 가능한 경로는 별도로 확인합니다.
  • 사람: 최소한 이동 속도·반응 시간·공간 익숙함이 다른 가상 참가자를 만듭니다.
  • 환경: 화재 발생과 출구 하나 폐쇄 같은 소수의 트리거부터 구현합니다.
  • 비교: 같은 사람 구성·랜덤 시드에서 개선 전후를 실행해 출구 추가나 안내 변경 효과를 확인합니다.
  • 기억: 실행 조건과 결과를 구조화해 저장하고 Agent가 이전 실험을 근거로 설명하도록 합니다.

Unity의 구현 가능성과 자원 소모를 먼저 확인하고, 감당하기 어려우면 웹 시뮬레이션으로 전환합니다. 엔진보다 조건을 바꾸고 결과를 비교하는 기능이 우선입니다.

제품의 전체 구조

수천·수만 개의 세계에서 배우고,
현장 대응을 계속 발전시킵니다.

AI는 행사 정보와 사용자 요청을 해석해 인원수·페르소나·사건 위치·시점·운영 조건을 제안합니다. 물리적 제약과 설정 근거를 검토한 뒤 세계를 실행하고 ID·랜덤 시드·모델·매뉴얼 버전을 기록합니다. 수천·수만 회는 처리량 검증 후 확장할 목표이며 현재 완료 수치가 아닙니다.

페르소나는 AI가 설정하거나 실제 행사 집계 정보를 반영합니다. NVIDIA의 Nemotron-Personas-Korea 공식 자료도 합성 프로필 후보입니다. 재난 시 이동·반응 행동은 별도로 모델링하고 검증해야 합니다. 아직 연동 완료한 자료는 아닙니다.

세계마다 위험이 시작되고 확산하는 과정, 미대피·혼잡·지연, 기존 매뉴얼의 누락과 충돌을 기록합니다. Agent는 근거 로그에서 원인 가설과 개선안을 제안하고, 같은 조건의 개선 전후 재실험으로 확인합니다. 세계 목록은 긴급성·심각도·현실성·근거 수준으로 정렬합니다. AI의 현실성 평가는 실제 발생 확률과 구분합니다.

LLM Wiki 또는 온톨로지 메모리는 조건·사건·대응·결과를 연결합니다. 관리자 승인 후 갱신된 매뉴얼을 다시 시험하고 운영에 반영합니다. 실시간 관제는 카메라 감지 → 상황 정리 → 관리자 승인 → 매뉴얼 실행 → 결과 확인으로 이어집니다.

화재 시 신고 지원, 총기 후보 감지 시 보안 담당 연락, 혼잡을 반영한 경로 분배, 등록 참가자의 참석·대피 완료·도움 요청 확인으로 확장합니다. 외부 연락·대피 안내는 관리자 승인 후 실행하며 미응답은 상태 미확인으로 구분합니다. 시연의 외부 연락은 모의 실행입니다. 현장 기록은 다음 시뮬레이션과 관제 개선의 근거가 됩니다.

07 / 확정 시연 기획

네 가지 장소, 서로 다른 위험.
하나의 학습·관제 시스템.

① AWS 행사장 ② 야구장 ③ 공연장 ④ 미국 학교의 총기 위협 상황을 시연 대상으로 설정합니다. 각 장소에서 사람과 환경을 바꾸고, 위험 세계를 찾아 개선 전후를 비교한 뒤 관리자 승인 기반의 대응까지 연결합니다.

네 시연 모두 제품 범위에 포함합니다. AWS 행사장을 실제 현장 검증의 기준 사례로 삼고, 나머지는 확보한 자료에 따라 재구성 또는 가상 공간으로 표시합니다. 실제 사고를 재현하거나 특정 시설의 안전성을 보증하는 시연은 아닙니다.

DEMO 01 / AWS 행사장

오늘 우리가 있는 공간을 먼저 검토합니다.

입력과 변화

  • 확보 예정인 현장 사진·영상·도면, 실제 사용 가능한 출구와 통로, 좌석·부스 배치.
  • 예상 인원과 행사 일정, 직원 배치, 현재 대응 매뉴얼.
  • 공간에 익숙한 참가자와 처음 온 참가자, 이동 속도·반응 시간·동행 여부가 다른 집단.
  • 화재·연기 후보 발생, 출구 일부 사용 불가, 행사 종료 시 동시 이동 등의 트리거.

보여줄 결과

어느 통로에서 병목이 생기는지, 어떤 참가자의 이동이 늦어지는지, 기존 매뉴얼에 해당 상황의 안내가 있는지 확인합니다.

개선 비교: 사용 가능한 출구 운영, 장애물 제거, 안내 인력 배치, 구역별 이동 순서 변경 전후를 같은 조건에서 비교합니다.

실시간 연결: 시험 영상/카메라 화재 후보 → 근거 화면 → 관리자 승인 → 모의 현장 연락 → 처리 기록.

현장 자료는 확보 후 Git에 올릴 예정입니다. 현재 확보 완료로 표시하지 않습니다. 대용량 영상은 Git LFS 또는 접근 가능한 별도 저장소 링크로 연결하고, 자료 버전·촬영 시점·실측 여부를 기록합니다. 행사 관계자의 결과 검토도 예정 단계입니다.

DEMO 02 / 야구장

큰 공간에서도 사람은 좁은 곳에 모입니다.

입력과 변화

  • 관람석 구역, 계단, 출입구, 매점·복도와 집결 공간.
  • 가족·동행 집단, 공간 익숙함, 이동 지원 필요성, 구역별 관람객 구성.
  • 경기 종료 동시 이동, 특정 출구 폐쇄, 일부 구역 연기, 우천에 따른 이동 변화.

관찰·개선·관제

관찰: 구역별 이동 완료 시간, 계단·복도 병목, 서로 반대 방향으로 이동하는 흐름의 충돌.

개선: 구역별 순차 퇴장, 안내 인력 재배치, 통로 운영 변경을 비교합니다. 다른 위험 구역으로 혼잡을 옮겼는지도 확인합니다.

관제: 구역별 혼잡 후보와 위험 감지 → 관리자 검토 → 승인된 구역 안내·요원 연락 → 결과 기록.

초기에는 관람석 일부와 연결 통로부터 모델링하고 구역 수를 확대합니다. 전체 야구장의 실제 수용 능력이나 밀집 위험 기준은 입력 자료와 검증 범위를 명시합니다.

DEMO 03 / 공연장

어두움·소음·동행 행동이 겹치는 공간

입력과 변화

  • 좌석형/스탠딩 구역, 무대, 펜스, 출구와 통로.
  • 동행자를 기다리거나 찾는 집단, 안내 인지 시간과 이동 속도가 다른 참가자.
  • 공연 종료, 정전, 화재·연기 후보, 특정 구역 이동 불가, 안내 전달 지연.

관찰·개선·관제

관찰: 안내를 늦게 인지한 집단, 출구 쏠림, 합류 지점과 좁은 통로의 혼잡.

개선: 구역별 안내, 통로 확보, 안내 인력과 집결 방식 변경 전후를 비교합니다.

관제: 화재·낙상·혼잡 후보 → 영상 근거와 위치 → 관리자 승인 → 구역 안내·의료/운영 담당 연락.

스탠딩 군중의 압력과 부상 추정은 단순 이동 모델만으로 검증되지 않습니다. 초기 화면은 혼잡·지연·미대피 지표를 중심으로 보여주고 위해 추정은 별도 모델 검증 이후 다룹니다.

DEMO 04 / 미국 학교 · 총기 위협

위협 감지와 승인된 보호 절차의 연결

입력과 변화

  • 가상 학교의 교실·복도·출입구, 구역별 재실 인원과 담당자 역할.
  • 교직원·학생 역할, 공간 익숙함, 안내 인지·도움 필요성의 차이.
  • 총기 의심 물체 감지, 특정 구역 위협 보고, 이동 경로 사용 제한, 통신 지연.

관찰·개선·관제

관찰: 위협 확인과 통보 지연, 매뉴얼 미정의 구역, 담당자 미응답, 위험 구역으로 이어지는 안내 여부.

개선: 연락 체계, 구역별 책임자, 승인·전달 절차의 누락을 보완하고 다시 시험합니다.

관제: 총기 후보 영상 → 관리자·보안 담당 확인 → 승인된 보호 절차와 모의 통보 → 수신·조치 확인.

실제 학생 개인정보와 실제 학교의 취약 지점은 사용하지 않는 가상 시연을 기본으로 합니다. 실제 학교에 적용할 때는 해당 기관이 승인한 현지 매뉴얼을 입력받습니다. 총기 위협을 화재와 같은 일괄 대피로 처리하지 않으며, 공격 경로나 공격 최적화는 생성하지 않습니다. 실제 긴급기관 연락은 시연에 포함하지 않습니다.

08 / 모든 시연의 공통 화면 흐름

조건 입력부터 조치 결과까지 한 이야기로

화면 1장소·요청 입력

인원과 페르소나, 자료 버전, 매뉴얼, 실험 요청

화면 2세계 생성·실행

AI 설정 제안, 제약 확인, 실제 실행 수와 진행 상태

화면 3위험 세계 탐색

긴급성·현실성·심각도·근거별 정렬과 타임라인 재생

화면 4개선·현장 대응

매뉴얼 변경 전후, 실시간 감지, 승인·모의 실행·기록

결과 카드에는 ‘관측된 현상 → 원인 가설 → 근거 이벤트 → 매뉴얼 부족점 → 권장 조치 → 재실험 결과’를 같은 순서로 표시합니다. 세계 목록에서는 피해가 큰 경우뿐 아니라 근거가 부족해 추가 검증이 필요한 경우도 분리합니다.

실행 수 표시: 생성한 조건 수, 실제 완료한 시뮬레이션 수, 실패·취소 수, 재생 가능한 세계 수를 구분합니다. 미리 계산한 결과와 현장에서 새로 실행한 결과도 구분합니다.

09 / 추가로 탐색할 수 있는 것

장소를 늘리기 전에, 네 장소의 검증 깊이를 높입니다.

우선 추가할 공통 실험

  • 수용 인원 비교: 인원을 단계적으로 바꾸고 어느 조건에서 병목이 커지는지 비교.
  • 복합 사건: 화재와 정전, 출구 제한과 통보 지연 등 조합을 비교.
  • 안내 실패: 방송 미인지·담당자 미응답·네트워크 단절 시 대체 절차 시험.
  • 접근성: 이동 지원이 필요한 집단과 동행 집단이 안내에서 누락되는지 확인.
  • 불확실성: 행동 가정과 시드를 바꾸었을 때 개선안이 일관되게 유효한지 확인.

관제와 연결할 발전 기능

  • 현재 상태 재실험: 확인된 출구 상태·구역 인원을 반영해 재평가. 연산 지연과 정보의 최신성을 표시.
  • 매뉴얼 비교: 기존안과 변경안의 통보·승인·조치 완료 시간을 비교.
  • 담당자 미응답: 승인된 연락 순서에 따라 다음 담당자에게 전달할 제안 생성.
  • 안부 확인: 등록 참가자의 대피 완료·도움 요청·미응답 상태를 구분.
  • 행사 후 복기: 감지·승인·조치 로그를 시뮬레이션 기록과 비교해 다음 행사에 반영.

추가 장소 후보는 지하철·환승역, 전시장, 대형 쇼핑몰, 지역 축제입니다. 초기 네 시연의 연결과 검증이 끝난 뒤 우선순위를 결정합니다.

10 / 자료 확보와 완료 기준

자료가 들어오면 구현 범위를 확정합니다.

  • 자료: 장소별 공간 구조·치수·출구 상태, 구역별 예상 인원, 일정·배치, 대응 매뉴얼, 카메라 구역.
  • 출처: 실제 현장/공개 도면/가상 구조를 구분하고 파일·출처·날짜·사용 범위를 기록.
  • 시뮬레이션: 동일 조건 재현, 이동 경로 유효성, 개선 전후 비교, 세계별 로그 보존.
  • 관제: 탐지 누락·오경보, 카메라에서 화면까지 지연, 관리자 승인, 모의 연락 성공·실패·중복 방지.
  • 시연 완료: 네 장소마다 최소 하나의 위험 사례와 개선 비교가 실제 결과로 연결되고, 실행되지 않은 기능은 기획 또는 모의 화면으로 표시.
  • 대규모 확장: 단일 세계의 실행 시간·메모리를 측정한 뒤 수천·수만 회의 실행 비용과 병렬 작업 수를 산정.

피해 감소율, 실제 발생 확률, 실제 시설의 안전 등급은 검증 없이 만들어내지 않습니다. 장소별 수치가 없을 때는 계산 전으로 표시합니다.

12 / 실시간 감지 구현 계획

화재는 YOLO,

AI Hub에서 받은 원본과 라벨을 학습·평가에 활용합니다. 행사 카메라 영상에서 위험 후보를 찾고, 위치·시각·근거 화면을 하나의 관제 이벤트로 전달합니다. 영상 인식 모델은 위험 후보를 만들고 Agent는 승인된 매뉴얼을 연결합니다.

화재·연기 · YOLO

구성: AI Hub 화재·연기 이미지와 라벨 → YOLO 미세조정 → 영상의 불·연기 후보 위치와 점수 → 관제 이벤트.

정상 장면과 화재처럼 보이는 유사 장면을 함께 평가합니다. 반복 프레임에서 경보가 지속되는지 확인하고, 같은 카메라의 중복 경보를 묶는 방식을 시험합니다.

현재: NHN 학습과 맥미니 추론을 확인했습니다. 오경보·누락이 남아 있으며 실제 행사장 카메라 성능은 별도 검증 대상입니다.

낙상 · YOLO Pose + 별도 분류기

계획: AI Hub 영상·행동 구간 라벨 → YOLO11n-pose로 관절 추출 → 동일 인물의 연속 자세 특징 → 낙상 분류 → 관제 이벤트.

몸통 기울기, 골반 높이 변화, 하강 속도, 쓰러진 자세의 지속시간 등을 특징 후보로 사용합니다. 초기에는 특징 기반 분류기로 비교하고, 데이터와 성능에 따라 LSTM·TCN 등 시간 모델을 검토합니다.

현재: 실제 초기 시험은 YOLO11n-pose와 간단한 로지스틱 분류기로 진행했습니다. 기존 YOLO Pose 경로를 유지하고 사람 추적·시간 특징·낙상 분류 성능을 개선합니다.

YOLO Pose의 역할과 실패 처리

YOLO11n-pose는 신체 관절 위치를 추출하는 모델이며 그 자체가 완성된 낙상 탐지기는 아닙니다. 사람별 추적, 관절 품질 확인, 시간 구간 판정이 별도로 필요합니다. 여러 사람의 관절을 한 사람의 움직임처럼 합치지 않습니다.

앉기·숙이기·눕기와 실제 낙상을 구분하고, 사람이나 관절이 충분히 보이지 않으면 ‘정상’이 아니라 ‘판단 보류’로 기록합니다. 기존 시험에서 나타난 작은 사람·가림·대상자 누락을 우선 검증합니다. 자세 추출 성공을 낙상 감지 성공으로 해석하지 않습니다.

데이터 출처: AI Hub 시니어 이상행동 영상. 데이터 라벨과 별도로 자세 추출 및 낙상 분류 파이프라인을 구성합니다.

NHN에서 학습하고, 맥미니에서 실제 입력으로 검증합니다.

탐지·누락·오경보·판단 보류·경보 지연을 함께 기록

운영 시험맥미니 관제 연결

실제 카메라 해상도와 동시 입력 수에서 지연·부하 확인

YOLO Pose가 추출한 관절 특징으로 별도 낙상 분류기를 학습합니다. 영상 ID별 학습·검증 분리를 유지하고, 다인 장면의 사건 당사자 추적과 맥미니의 실제 입력 부하를 검증합니다.

총기 감지는 별도 데이터·전용 가중치·평가가 필요한 YOLO 후보 기능입니다. 화재 모델의 성공을 총기 감지 성능으로 해석하지 않습니다. 기존 기본 모델만으로 총기 탐지가 된다고 표시하지 않습니다.

위험 후보 감지 → 근거·위치 표시 → 관리자 승인
→ 승인된 연락·안내 → 수신·조치 결과 기록

개발 하네스와 개발 에이전트는 OpenAI 모델만 사용합니다. 제품의 비전 기능에는 사용자가 허용한 YOLO 계열 모델을 사용합니다. 낙상의 현재 선택은 YOLO Pose이며 MediaPipe는 채택하지 않습니다. 외부 연락과 대피 안내의 관리자 승인 원칙은 유지합니다.

팀 공유용 기획 설명 · 페르소나, 트리거, Agent 메모리는 구현 목표입니다. 이 페이지의 예시는 검증된 재난 예측 결과가 아닙니다.
